## 晚高峰那三个小时，卡在哪

三个地方：共享带宽被邻居跑满、回程绕路、宿主机超售。这三条跟 CPU 型号、内存大小基本无关，所以看配置单判断不出晚高峰表现。

共享带宽最常见。宣传页写“100M 大带宽”，实际是同一台母机上几十上百个 VPS 分这条 100M 出口。白天没人跑流量，你能测出很高的速度；到了晚上八点到十一点，邻居开始下载、看直播、跑备份，这条管子被挤爆，你实际分到的可能连 5M 都不到。5M 独享在晚高峰的体验经常好过 100M 共享，原因就在这里。

绕行是第二个。国内三大运营商访问海外默认走公共 163 骨干网，这条网承载了全国 90% 以上的国际流量。晚高峰出口超载，数据包排队甚至被直接丢弃，运营商还会对普通流量做 QoS 限速。更麻烦的是路由本身绕路：廉价机器从洛杉矶发出，先绕日本、再绕欧洲，最后才进中国大陆，本来 150ms 的物理极限被绕成 300ms 以上，抖动跟着变大。

超售看一个指标就够。在机器上执行 `top`，如果 `%st`（Steal Time，被宿主机“偷走”的 CPU 时间）长期高于 10%，说明这台母机上你的邻居在抢你的 CPU。磁盘 I/O 也会跟着堵，数据库查询会明显变慢。

## 下单前先用测试 IP 跑三步

官方给了测试地址：德国法兰克福 `fralg.akkocloud.com`，美西圣何塞 `sjclg.akkocloud.com`（测试 IP 45.9.10.146）。买之前 ping 一下、跑个 traceroute，看自己所在地区到机房的真实表现。

具体三步：

第一步，连续 ping 五百个包，看丢包率。高于 1% 说明晚上会不稳。


ping -c 500 目标IP


第二步，用 mtr 定位丢包发生在哪一跳。


mtr -rwzbc 100 目标IP


中间某个 59.43 节点丢包、但最后一跳正常，那是 ICMP 限速，不是线路问题。最后一跳丢包超过 1%，这家可以放弃。

第三步，把测试放到晚高峰去跑。单次测试看不全，用 crontab 在 20:00–23:00 每五分钟记录一次：


*/5 20-23 * * * /usr/bin/mtr -rwzbc 100 目标IP >> /var/log/vps_evening_mtr.log


第二天看日志里 5 分钟粒度的延迟和丢包曲线，比任何宣传页都直接。

机器开出来之后再补两个检查：`top` 看 `%st` 是否长期高于 10%，`iperf3` 测并发吞吐看带宽有没有大幅缩水。这两项决定你遇到的是线路问题还是邻居问题。
